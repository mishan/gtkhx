# R3.3.e-4: production switch in `src/network.c`

> Working notes — not yet implemented. The sub-phases below are the
> proposal; landing order can shift if review suggests a different cut.

## What's already done

R3.3.a–R3.3.e-3 ship the entire hxnet surface needed to drive a
production connection from Rust:

- The Connection actor reads / writes Hotline frames against any
  `AsyncRead + AsyncWrite + Unpin + Send + 'static` transport
  ([R3.3.a]).
- A C-callable FFI lets the C side adopt a TCP socket fd, send
  outbound frames, and either poll or callback-receive inbound ones
  ([R3.3.b], [R3.3.e-1]).
- Cipher (Blowfish-OFB-64 / ChaCha20-Poly1305) and compression
  (GZIP / LZ4 / ZSTD) adapters wrap any `AsyncRead + AsyncWrite`
  inner ([R3.3.c], [R3.3.d]).
- `hxnet::transform::compose` layers cipher + compression onto a
  transport in HOPE order; `Connection::spawn_boxed` accepts the
  resulting type-erased duplex; the C side describes the stack with
  a flat `HxnetTransformConfig` struct ([R3.3.e-2], [R3.3.e-3]).

What's left is the C-side rewire — making `src/network.c` actually
*use* that surface for the production control connection instead of
the existing `GIOStream` + GPollable-source path.

## What R3.3.e-4 has to change

The relevant `network.c` surface, as it stands today:

- **Connection setup** runs through `GSocketClient` /
  `GSocketConnection` / optional `GTlsConnection`, ending with the
  long-lived `GIOStream` stored in `current_conn`.
- **Reads** are driven by `g_pollable_input_stream_create_source` on
  the input side of `current_conn`. `control_on_readable` loops:
  `htlc_stream_read` into `htlc->read_in`, then `hx_decode` until
  no more frames decode; each completed frame is dispatched via
  `htlc->rcv`.
- **Writes** are queued into `htlc->out` by `hlwrite` /
  `hlwrite_chunks`. They arm a write source via
  `control_arm_write_source`; `control_on_writable` drains the queue
  via `htlc_stream_write`.
- **Cipher + compression are applied in place** to the buffered
  bytes: `compress_encode` overwrites the queued bytes with the
  compressed form, then `cipher_encode` overwrites again with the
  encrypted form. `hx_decode` inverts both on the read side.
- **HOPE handshake** negotiates cipher + compression after connect,
  before any application traffic. The negotiated state lands in
  `htlc->cipher_*` / `htlc->compress_*`.
- **Ping keepalive** uses `g_timeout_add_seconds` and calls `hlwrite`.

In the hxnet model, the cipher + compression layers move into the
Rust transport (`compose` builds the stack from a
`HxnetTransformConfig`), and the C side only sees plaintext frames.
That changes nearly every site that touches the byte stream:

| Today | hxnet-shaped |
|---|---|
| `hlwrite` → pack → `control_arm_write_source` → encode in place → drain via `control_on_writable` | `hlwrite` → pack → `hxnet_connection_send_frame` of one complete frame |
| `control_on_readable` → `htlc_stream_read` → `hx_decode` (which calls cipher_decode + compress_decode) → `htlc->rcv` | `on_event` callback → dispatch frame body into `htlc->rcv` directly; no decode call |
| `compress_encode` / `cipher_encode` invoked from `hlwrite` after pack | Not called; cipher + compress are handled by the `compose`-built stack inside hxnet |
| `hx_htlc_close` clears `current_conn` (which closes the fd) | Calls `hxnet_connection_destroy`, which drops the cmd channel, the actor exits, the wrapped `TcpStream` closes the fd |
| `control_remove_all_sources` removes GPollable sources | No equivalent — there are no GPollable sources for the hxnet path |

The HOPE handshake itself can stay in C — it runs over plain TCP
before any cipher / compression is active. The handover point is
"HOPE finished negotiating; now hand the fd to hxnet with the
transform config we just decided on."

## TLS is out of scope

TLS-wrapped connections use a `GTlsConnection` over the underlying
`GSocketConnection`, with the kernel fd hidden inside the TLS
machinery. hxnet's FFI adopts a raw TCP fd via
`from_raw_fd` — it has no TLS support today. Porting TLS into the
Rust transport is a Phase 7 effort (see `docs/tls-scoping.md`),
not R3.3.e-4.

For now, R3.3.e-4 only switches non-TLS connections to hxnet. TLS
connections keep the existing `GIOStream` + GPollable path. The
network.c code keeps both branches in parallel until the TLS
migration lands.

## Proposed sub-phases

### R3.3.e-4a — bridge dispatch module

Add a self-contained `src/hxnet_bridge.{c,h}` module exposing two
C entry points that the eventual `on_event` / `on_shutdown`
callbacks will wrap:

- `hx_bridge_dispatch_frame(htlc, hxnet_frame_const_ptr)` — translates
  a plaintext frame into the existing rcv dispatch. Populates
  `htlc->in` with `[header bytes | body bytes]`, calls
  `htlc->rcv(htlc)` for the header, then calls it again for the
  body, matching what `control_on_readable` does today.
- `hx_bridge_dispatch_shutdown(htlc, hxnet_shutdown_reason_int)` —
  marshals the shutdown reason back into `hx_htlc_close` semantics.

Both functions are called from a `GMainContext` callback, so they
run on the GLib main thread. They reuse the existing rcv-side
plumbing (no new dispatch tables; no new `htlc->in` state).

Ships with:

- Unit tests for the dispatch translation against synthetic
  `HxnetFrame`s. Verifies the rcv path sees what it expects.
- No `network.c` changes. The bridge functions are unreferenced by
  production today; R3.3.e-4b is the first consumer.

This sub-phase is small enough to land cleanly and lets reviewers
focus on the translation contract before the wider lifecycle
refactor lands.

### R3.3.e-4b — bridge install / send / uninstall helpers

Extend the bridge module with the C-side glue that wraps hxnet's
callback FFI:

- `hx_bridge_install_passthrough(htlc, fd)` — adopts `fd`, calls
  `hxnet_connection_spawn_fd_with_transforms_and_callback` with a
  cipher=NONE / compression=NONE config, and registers the
  bridge's internal `bridge_on_event_cb` /
  `bridge_on_shutdown_cb` trampolines that route through
  `hx_bridge_dispatch_frame` / `hx_bridge_dispatch_shutdown`.
- `hx_bridge_is_installed()` — gate the production code paths
  use to choose between the new (hxnet) and legacy (GIOStream)
  read / write loops.
- `hx_bridge_send_frame(buf, len)` — wraps
  `hxnet_connection_send_frame`.
- `hx_bridge_uninstall()` — wraps `hxnet_connection_destroy`.

The bridge module is now end-to-end linkable against the
production rust_hxnet_dep (added to src/meson.build's gtkhx
executable). The Tier 1 test continues to stub the hxnet
symbols so `cargo test`–free CI smoke runs stay quick;
production wiring (the env-var gate in network.c + the
`hlwrite` / `hx_htlc_close` routing) lands in R3.3.e-4c.

### R3.3.e-4c — opt-in env var: `GTKHX_USE_HXNET`

Add the lifecycle wiring without changing the default behaviour:

- `network.c` checks `g_getenv("GTKHX_USE_HXNET")` after the connect
  + magic exchange completes. When set (and TLS is not active):
    1. Run the HOPE handshake over the existing GIOStream to learn
       the cipher / compression choice.
    2. Tear down the GIOStream (drop sources, capture the underlying
       fd via `g_socket_get_fd` + `dup`, close the `GIOStream` without
       closing the fd).
    3. Build a `hxnet_transform_config` from `htlc->cipher_*` /
       `htlc->compress_*`.
    4. Call `hxnet_connection_spawn_fd_with_transforms_and_callback`,
       storing the returned handle as a new
       `current_hxnet_conn` global.
- New `current_hxnet_conn != NULL` gates all read / write paths:
    - `hlwrite` / `hlwrite_chunks` route the packed frame through
      `hxnet_connection_send_frame` instead of `compress_encode` +
      `cipher_encode` + `control_arm_write_source`.
    - `control_arm_write_source` becomes a no-op when the hxnet
      handle is live.
    - `control_on_readable` is never installed (the callback FFI
      drives reception instead).
- `hx_htlc_close` calls `hxnet_connection_destroy` when the handle
  is live.

Tests:

- Unit tests for the two-path routing (env-var set vs unset)
  against a mock server that exercises both branches.
- Tier 3 against mhxd with `GTKHX_USE_HXNET=1` — verifies
  passthrough config (cipher=NONE, compression=NONE) and the
  HOPE-negotiated cipher path (Blowfish; ChaCha20-Poly1305 if
  mhxd's HOPE supports it on the test target).
- A regression run with the env var unset confirms the old path
  is untouched.

### R3.3.e-4d — flip the default

Once R3.3.e-4c is stable across the Tier 3 matrix, flip the gate
so hxnet is the default and `GTKHX_USE_HXNET=0` opts out. Old path
stays in place as the kill-switch.

### R3.3.e-4e — delete the legacy path

After R3.3.e-4d has soaked through one or two releases, remove
the `GIOStream` read / write loop, the in-place
`compress_encode` / `cipher_encode` calls, and the GPollable
source machinery. `control_*` helpers go away.

TLS connections still keep the `GIOStream` path until Phase 7
moves TLS into Rust; R3.3.e-4e only deletes the non-TLS legacy.

### R3.3.e-5 — Tier 3 integration verification

Cross-reference test against the full Tier 3 matrix:

- **mhxd** (vendored): controlled / repeatable baseline. Plain
  HOPE-Blowfish path.
- **Janus** (VesperNet): modern server with chat-history
  extension. Use the existing Docker harness.
- **hlserver.com** (1.0/1.2 behaviour): no HTLS_DATA_VERSION,
  rejects unknown opcodes. Exercises the legacy-server fallback
  path without HOPE.
- **Mobius** (TLS over separate port): regression-only;
  hxnet path is not taken because TLS keeps the GIOStream
  branch.

Each gets a Tier 3 test that runs against the published binary
and verifies: connect succeeds, login succeeds, a chat message
round-trips, disconnect is clean. Tests pass with default
behaviour after R3.3.e-4c lands.

## Open questions for review

1. **Send-path framing assumption.** `hxnet_connection_send_frame`
   wants one complete Hotline frame per call. Today `hlwrite`
   builds the frame in `htlc->out` via `hlpack` and the queue
   drains incrementally. The R3.3.e-4b flow packs into a local
   buffer (not `htlc->out`) and ships it in one `send_frame` call.
   Need to confirm no caller relies on the partial-frame state
   in `htlc->out`.

2. **fd ownership at the handover.** `g_socket_get_fd` returns the
   fd `GSocketConnection` owns; we need to `dup` it (or
   `g_socket_close` the wrapper without closing the fd, then take
   ownership ourselves). `tokio::net::TcpStream::from_raw_fd`
   wants ownership.

3. **HOPE bytes in flight.** After HOPE negotiation, the GIOStream's
   input buffer might have post-HOPE bytes already pulled from the
   kernel but not yet drained. Those bytes need to either:
   (a) be consumed by HOPE completely, or
   (b) be fed to hxnet's read path before the actor starts pulling
   from the fd.
   Plan (a) is cleaner; need to verify HOPE handshake reads only as
   much as it negotiates.

4. **Test harness for R3.3.e-4b.** The `GTKHX_USE_HXNET=1` path
   needs an end-to-end test that drives a Hotline connection
   against a controlled peer. Tier 3 against mhxd is the obvious
   integration target; Tier 2 can mock the wire with a Go fixture
   server (we already have one for chat-history in
   `tests/integration/mock-server/`).
